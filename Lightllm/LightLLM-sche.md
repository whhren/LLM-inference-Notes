# LightLLM 请求调度策略实验基本信息
## 1.1 研究的问题及步骤
LightLLM中使用了请求长度预测的方法，来为请求提前分配内存，再根据内存使用情况来控制请求的准入。这个请求长度的预测是通过历史请求的输入长度和输入长度来估计得到的。虽然大部分论文都提出相同请求的输出长度是随机变化的，但是本人还是想通过实验探究一下利用这个输出长度的信息，能否通过改变请求进入的时间，进而提升部分请求的延迟。也就是说优化请求的SLO(Service Level Objective)

请求的延迟也就是下面实验中的Latency包含：请求在队列中排队的时间和请求执行的时间(Prefill的时间和Decode的时间)

本实验会从下面几个方面探讨：

- 1. 请求的输入和输出是否存在某种关系
- 2. 请求输出长度的分布
- 3. 改变调度策略是否会提升部分请求的延迟，以及恶化部分请求的延迟
- 4. 不同输出长度区间的平均延迟

实验结果并没有太大意义，效果基本没有，仅供参考。目前没有在稍大一点的模型上进行实验。

## 1.2 实验环境与配置

- **硬件：** NVIDIA RTX 4060 8GB
- **模型：** Llama-3.2-1B-Instruct
- **数据集：** ShareGPT_V3_unfiltered_cleaned_split，每次实验使用 4000 条请求
- **并行配置：** TP=1，DP=1
- **推理参数：** `mem_fraction=0.7`，`max_req_total_len=4096`，`running_max_req_size=16`，`batch_max_tokens=1024`

LightLLM 采用多进程架构，本实验主要在 Router 调度侧进行修改，不直接调整模型执行端的核心推理逻辑。这种设计能够减少对执行端代码的侵入，并便于独立分析调度策略的影响。

需要注意的是，调度策略仍可能通过改变请求进入批次的顺序、批次构建过程及请求准入时机，间接影响执行端的负载和整体推理性能。因此，实验将通过吞吐量、延迟、TTFT 和 ITL 等指标，评估不同调度策略对系统性能的实际影响。



# 2.实验部分
## 2.1 请求输入和输出长度的相关性、输出长度的分布

**请求输出长度的分布**

![5000 条请求的输出长度分布](images/fcfs_rate10_req5000_output_distribution.png)

不同请求的输出长度存在明显差异，说明请求的生成负载并不均匀，为研究基于请求长度的调度策略提供了依据。

**请求输入和输出长度的相关性**
![5000 条请求下的输入与输出长度关系](images/fcfs_rate10_req5000_input_vs_output.png)

Pearson 相关系数（$r$）用于衡量两个变量之间的**线性相关程度**，取值范围为 $[-1,1]$。其中，正值表示正相关，负值表示负相关，绝对值越大，线性相关程度通常越强。

共 5000 条请求的实验中，输入长度与输出长度的 Pearson 相关系数为 **0.43**，呈正相关，但相关性较为有限。输入较长的请求可能倾向于产生较长的输出，但仅凭输入长度仍难以准确预测实际输出长度。

这一结果说明，**请求输入长度虽然不是输出长度的准确预测指标，但仍然包含一定的长度信息，可作为短作业优先（SJF）等调度策略的参考依据。** 因此，基于请求长度进行排序具有一定的合理性，但实际效果仍需通过对比实验验证。


## 2.2 不同策略对请求延迟是否有影响

说明：针对不同的rate只测试了一次，rate是每秒发送请求的数量。设备运行时平均处理时长是2-3请求每秒。在3的时候基本上就会有排队的现象。

参数说明：
| 指标 | 含义 |
|---|---|
| 实际吞吐量 | 系统实际完成请求的速率（req/s），用于衡量请求处理能力 |
| 平均延迟 | 所有请求从发起到完成的平均耗时（ms） |
| 平均 TTFT | 平均首 Token 生成时间（Time To First Token），反映用户等待模型首次响应的时间 |
| 平均 ITL | 平均相邻输出 Token 之间的时间间隔（Inter-Token Latency），反映生成阶段的逐 Token 响应速度 |
| Latency P10～P90 | 延迟的第 10～90 百分位数。例如，P90 表示 90% 的请求延迟不超过该值 |
| Latency P99 | 延迟的第 99 百分位数，用于观察长尾延迟表现 |

# 3. 结果分析
本次实验表明，在当前模型、硬件及测试配置下，简单的请求排序策略尚未展现出稳定的整体性能提升。不过，这并不意味着这些策略在其他模型或负载条件下同样无效。不同模型的 Prefill、Decode 计算开销及资源占用可能存在差异，调度策略的实际收益仍需进一步验证。

后续需要在更大规模的模型上开展实验，并结合不同负载下的延迟分布，进一步分析各调度策略的适用条件。

如果你对这方面感兴趣可以看看这些论文：
- **Past-Future Scheduler for LLM Serving under SLA Guarantees**（ASPLOS 2025，CCF A）：ligthllm就是这篇文章提出来的。结合历史输出长度分布与未来时刻的显存需求估计，优化请求准入，减少请求驱逐和排队等待。[论文链接](https://arxiv.org/abs/2507.10150)

- **Beyond Prediction: Tail-Aware Scheduling for LLM Inference**（ICML 2026，CCF A）：提出无需显式预测输出长度的调度方法，通过动态优先级调整与缓存感知抢占，优化 LLM 推理的尾延迟。[论文链接](https://proceedings.mlr.press/v306/li26n.html)

- **Scheduling LLM Inference with Uncertainty-Aware Output Length Predictions**（ICML 2026，CCF A）：针对输出长度预测存在的不确定性，采用概率分布描述请求输出长度，为短作业优先调度提供更合理的依据。[论文链接](https://proceedings.mlr.press/v306/zheng26ae.html)
